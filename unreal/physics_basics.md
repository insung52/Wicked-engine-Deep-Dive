# 물리 엔진 기초 개념

렌더링 엔진에 물리를 붙이기 전에 알아야 할 기본 개념.  
코드 없이 직관적으로 이해하는 것이 목표.

---

## 물리 엔진이 하는 일

한 줄로: **"매 프레임마다 물체들의 미래 위치를 계산해주는 소프트웨어"**

UE 에디터에서 공을 집어서 던졌을 때 일어나는 일:
- 공이 포물선을 그리며 날아감 → 중력 계산
- 바닥에 닿으면 튕김 → 충돌 감지 + 반응 계산
- 구석에서 멈춤 → 마찰력 계산

이 모든 계산을 렌더링 엔진 대신 해주는 것이 물리 엔진.  
렌더링 엔진은 물리 엔진이 "여기 있어" 라고 알려준 위치에 그림만 그리면 됨.

```
물리 엔진: "공은 지금 (3.2, 0.8, 1.5) 에 있고, 아래로 기울어져 있어"
렌더링 엔진: "알겠어, 거기에 공 그릴게"
```

---

## 핵심 개념 5가지

### 1. 강체 (Rigid Body)

물리 엔진이 다루는 가장 기본 단위. **변형되지 않는 단단한 물체**.

현실에서 공을 표현하려면:
- 위치 (Position): 공이 어디 있나? (x, y, z)
- 회전 (Rotation): 공이 어떻게 기울어져 있나?
- 선속도 (Linear Velocity): 얼마나 빠르게 어느 방향으로 날아가나?
- 각속도 (Angular Velocity): 얼마나 빠르게 회전하고 있나?
- 질량 (Mass): 무게가 얼마나 되나?

물리 엔진은 이 6가지 값을 매 프레임 업데이트한다.

```
[현재 상태]          [물리 계산]          [다음 상태]
위치 (3, 0, 5)  →   중력 적용           →  위치 (3, 0, 4.8)
속도 (0, 0, -1) →   F=ma로 가속도 계산   →  속도 (0, 0, -1.2)
```

> **UE에서 경험한 것**: 에디터에서 물체에 "Simulate Physics" 체크하면 이 강체 시뮬레이션이 시작됨.

---

### 2. 충돌 감지 (Collision Detection)

두 물체가 겹쳤는지 검사하는 과정. 두 단계로 나뉨.

**Broad Phase (빠른 1차 검사)**  
모든 물체 쌍을 정밀하게 검사하면 너무 느리니까, AABB(축 정렬 박스)로 대략 겹치는지만 먼저 확인.

```
[물체 A의 박스]   [물체 B의 박스]
  ┌────┐            ┌────┐
  │    │            │    │    → 겹침 없음 → 스킵
  └────┘            └────┘

  ┌────┐
  │  ┌─┼──┐
  └──┼─┘  │         → 겹침! → Narrow Phase로 넘김
     └────┘
```

**Narrow Phase (정밀 2차 검사)**  
실제 콜리전 형태(구, 캡슐, 볼록다각형 등)로 정확히 겹친 깊이와 방향 계산.  
출력: **충돌 접점(Contact Point)** + **침투 깊이(Penetration Depth)** + **충돌 법선(Normal)**

> **UE에서 경험한 것**: 에디터의 콜리전 뷰어에서 파란/초록 와이어프레임으로 보이는 것들이 Narrow Phase에 쓰이는 형태.

---

### 3. 충돌 반응 (Collision Response)

겹쳤다는 걸 알았으면, 어떻게 튕길지 계산.

**임펄스 (Impulse) 방식**: 물체에 순간적인 힘을 가해서 속도를 바꿈.

```
공이 바닥에 충돌:
  1. 충돌 법선 방향으로 침투 깊이만큼 위치 보정 (물체가 겹치지 않도록)
  2. 반발 계수(Restitution)에 따라 속도 반전 (완전탄성 = 1.0, 완전비탄성 = 0.0)
  3. 마찰 계수(Friction)에 따라 접선 방향 속도 감소
```

> **UE에서 경험한 것**: Physics Material에서 Restitution(탄성), Friction(마찰) 값 조절하던 것.

---

### 4. 솔버 (Solver)

현실에는 물체가 여러 개이고, 동시에 여러 충돌이 일어난다.  
솔버는 **"모든 충돌과 제약조건을 동시에 만족하는 답을 찾는 알고리즘"**.

예: 탱크의 바퀴 4개가 동시에 지면에 닿을 때
- 바퀴 4개 각각의 충돌 반응이 차체에 영향
- 차체 움직임이 다시 각 바퀴에 영향
- 이걸 반복적으로(iterative) 풀어서 수렴시킴

UE5의 Chaos는 **PBD(Position Based Dynamics)** 계열 솔버 사용.  
(비교: UE4의 PhysX는 impulse 기반 솔버)

> **이전 분석에서 나온 것**: `STAT_ChaosTick` 2.63ms가 바로 이 솔버 실행 시간. 30대 탱크도 2.63ms밖에 안 걸린 이유 — 솔버가 워커 스레드에서 병렬로 한번에 다 처리하기 때문.

---

### 5. 적분 (Integration)

힘 → 가속도 → 속도 → 위치 순서로 업데이트하는 수학적 과정.

```
F = m * a                    (뉴턴 제2법칙)
a = F / m                    (가속도 계산)
v(t+dt) = v(t) + a * dt      (속도 업데이트)
x(t+dt) = x(t) + v * dt      (위치 업데이트)
```

이걸 매 프레임(dt = 프레임 시간)마다 반복.  
dt가 크면(저FPS) 시뮬레이션이 불안정해지는 이유가 여기 있음.

물리 엔진은 보통 **고정 타임스텝(Fixed Timestep)** 사용: 렌더 프레임과 무관하게 1/60초 단위로 물리를 업데이트.

## 게임 루프에서 물리의 위치

```
매 프레임:

┌─────────────────────────────────────────────┐
│  1. 입력 처리                                │
│     키보드/마우스 → 캐릭터에 힘(Force) 적용   │
├─────────────────────────────────────────────┤
│  2. 물리 스텝 (Physics Step)                 │
│     a. 힘 → 가속도 → 속도 → 위치 (적분)      │
│     b. 충돌 감지 (Broad + Narrow Phase)      │
│     c. 충돌 반응 계산 (솔버)                  │
│     d. 위치/속도 확정                         │
├─────────────────────────────────────────────┤
│  3. 결과 반영                                 │
│     물리 위치 → 렌더링 오브젝트 transform 복사│
├─────────────────────────────────────────────┤
│  4. 렌더링                                   │
│     확정된 위치에 그림 그리기                  │
└─────────────────────────────────────────────┘
```

물리 엔진은 **2번**만 담당. 렌더링 엔진이 이 2번을 실행시키고, 결과를 4번에 넘겨주는 연결 작업을 함.

## 렌더링 엔진이 물리를 "붙인다"는 게 무슨 뜻인가

렌더링 엔진 혼자서는 물체가 어디 있어야 할지 계산을 못 함.  
물리 엔진은 렌더링을 전혀 모름.  
둘을 연결하는 **글루 코드(Glue Code)** 가 필요.

```
렌더링 엔진 (UE5)          물리 엔진 (Chaos)
      │                          │
      │  ① 물리 바디 등록         │
      │  (Actor 생성 시)          │
      ├─────────────────────────►│  "이런 모양의 물체가 여기 있어"
      │                          │
      │  ② 물리 스텝 실행         │
      │  (매 프레임)              │
      ├─────────────────────────►│  "dt만큼 시뮬레이션해줘"
      │                          │  (내부에서 충돌, 솔버 등 실행)
      │                          │
      │  ③ 결과 가져오기          │
      │◄─────────────────────────┤  "끝났어, 각 물체 위치는 이래"
      │                          │
      │  ④ Transform 업데이트     │
      │  (렌더 오브젝트에 반영)   │
```

UE5에서 이 4단계가 구체적으로 어떤 함수로 구현됐는지가 `ue5_physics_integration.md` 의 내용.

## CPU vs GPU 물리

### 결론부터

| 유형 | 실행 위치 | 이유 |
|------|-----------|------|
| 강체(Rigid Body) 시뮬레이션 | **CPU** | 데이터 의존성 때문 |
| 파티클 물리 (수만~수백만 개) | **GPU** | 독립적 연산이라 병렬화 유리 |
| 천(Cloth) 시뮬레이션 | GPU 또는 CPU | 구현에 따라 다름 |
| 유체(Fluid) 시뮬레이션 | **GPU** | 격자 기반이라 병렬화 유리 |

Chaos, PhysX, Bullet, Jolt — 주요 게임 물리 엔진은 모두 **CPU에서 실행**된다.

---

### GPU가 잘하는 것 vs 물리가 필요한 것

GPU는 **"같은 연산을 독립적인 데이터에 대량으로"** 할 때 빠름.

```
GPU가 잘하는 것:
  픽셀 10,000,000개 → 각자 독립적으로 셰이더 실행 → 병렬 완벽

물리 충돌 솔버:
  공 A가 B를 밀어 → B가 C를 밀어 → C가 다시 A에 영향
  → 앞 결과가 뒤에 영향을 줌 (데이터 의존성)
  → GPU 병렬화가 근본적으로 맞지 않음
```

강체 물리의 핵심인 **솔버(Solver)는 반복적(iterative)이고 순차적인 계산**이라 GPU의 SIMD 구조와 궁합이 나쁨.

---

### 복잡한 씬이면 GPU가 더 효율적이지 않나?

직관적으로는 맞는 말이지만, 실제론 두 가지 문제가 있음.

**문제 1: GPU → CPU 데이터 전송 비용 (Readback Latency)**

```
물리 결과를 게임 로직에서 써야 하는 상황:

[CPU] "공이 어디 있어?"
  ↓ (GPU에서 계산 중이면...)
[GPU → CPU 전송 요청]
  ↓ (수 밀리초 대기)
[CPU] "이제 좌표 받았어"

GPU는 비동기로 동작하기 때문에,
결과를 CPU로 가져오는 순간 파이프라인이 멈춤.
```

물리 결과는 "이 공이 벽에 맞았나? → 데미지 처리 → 사운드 재생" 처럼 즉각적으로 게임 로직에 연결돼야 해서, GPU에 놔두면 이 readback 비용이 항상 발생함.

**문제 2: 강체 개수 자체가 GPU 효율 구간 밖**

GPU가 CPU를 압도하는 건 수십만 개 이상의 독립 연산부터. 게임의 강체 수는 보통 수백~수천 개 수준 — CPU 멀티코어로 충분히 처리 가능한 범위.

---

### 그러면 GPU 물리는 언제 씀?

**파티클 (Niagara GPU 파티클)**
- 각 파티클이 독립적 → 병렬화 완벽
- 수십만 개도 GPU에서 실시간 처리 가능
- 게임 로직에 직접 연결되지 않아도 됨 (비주얼 목적)
- UE5의 Niagara GPU 파티클이 이 방식

**천(Cloth)**
- 천 조각 = 수천 개의 점이 스프링으로 연결된 구조
- 각 점의 계산이 비교적 독립적 → GPU 병렬화 유리
- Chaos Cloth (UE5), PhysX Cloth 등이 GPU 옵션 제공

**비주얼 전용 파괴(Destruction)**
- 건물이 무너질 때 수천 개 파편 → 게임플레이에 영향 없음
- 게임 로직 연결 불필요 → readback 문제 없음
- GPU에서 돌려도 됨

**유체(Fluid)**
- 격자(voxel grid) 기반 계산 → 각 격자 독립적 → GPU 완벽
- 주로 비주얼 이펙트용 (실시간 게임플레이 물리로는 너무 무거움)

---

### UE5 Chaos 구체적으로

```
Chaos 강체 솔버    → CPU (TaskGraph Worker)   ← 30탱크 2.63ms
Niagara 파티클    → GPU (Compute Shader)
Chaos Cloth       → CPU (기본) / GPU 옵션 있음
Chaos Destruction → CPU (게임플레이 연동 있는 부분)
```

이전에 측정한 **2.63ms가 CPU Worker 스레드에서 실행된 것**이 여기서 확인됨.  
만약 GPU 물리였다면 Insights에서 GPU 타임라인에 잡혔겠지만, TaskGraph Worker(CPU) 행에 잡힌 것.

---

### 정리: 언제 CPU, 언제 GPU를 쓸지

```
게임 로직에 연결되어야 함?
  → YES → CPU (readback 비용 감당 불가)
  → NO  → GPU 고려 가능

물체 수가 얼마나 됨?
  → 수천 개 이하 → CPU 멀티코어로 충분
  → 수만 개 이상 + 독립적 → GPU 유리

연산이 순차적으로 의존적임?
  → YES (강체 솔버, 충돌 체인) → CPU
  → NO (파티클, 천, 유체) → GPU
```
